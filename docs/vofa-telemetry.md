# 用 VOFA+ 查看 A 板无线遥测

## 编译固件

日常在 [`config/_vofa/vofa_config.h`](../config/_vofa/vofa_config.h) 只修改 `VOFA_OBSERVATION_PROFILE`：`1` 为功率/超级电容，`2` 为卡尔曼（默认）。保持 `config/00_flash/board_flash_config.h` 中的 `BOARD_FLASH_1_VOFA_TELEMETRY_MODE=2`，重新构建并烧录后切换用途。固件和烧录脚本共用该默认档位，显式构建参数或旧自定义预设可覆盖它。两档均通过 UART7 输出 JustFloat，使用 **230400 / 8N1，96 通道**。功率档保留 20 ms 最新快照；远端融合卡尔曼档逐次捕获滤波调用，正常约 50 Hz，串口就绪后按队列顺序发送。用 VOFA+ 自带功能导出原始 CSV，不需要配置字段、改列名、换算单位或转换文件。修复后的实车复采见[卡尔曼重新采集步骤](kalman-recapture.md)。

| 用途选项 | schema | 内容 |
| --- | --- | --- |
| `VOFA_OBSERVATION_PROFILE=1` | `4` | 四轮请求/最终命令、功率计、控制周期预算/保护、最新策略、超电与裁判 |
| `VOFA_OBSERVATION_PROFILE=2`（默认） | `5` | 轮速/目标/融合速度、源 IMU、真实滤波输入、尝试/更新/重置计数与实际参数 |
| `VOFA_OBSERVATION_PROFILE=0` | `2/3` | 保留旧 64/72 路完整观测布局，按下文旧表解读 |

用途选项仅在传输模式 `2` 生效。`VOFA_TELEMETRY_ENABLE=0` 关闭输出；旧模式 `0/1` 忽略用途选项，继续使用原格式。

| `VOFA_TELEMETRY_MODE` | 用途 | VOFA+ 协议 |
| --- | --- | --- |
| `0` | 原有 19 路遥测，默认 20 ms / 50 Hz，通道与单位保持不变 | JustFloat |
| `1`，主板开启 CAN IMU 接收 | schema 3，72 路观测数据，每组一行，发送间隔至少 80 ms | FireWater |
| `1`，未开启 CAN IMU 接收 | schema 2，64 路本板观测数据，发送间隔至少 80 ms | FireWater |
| `2`，用途 `0`，主板开启 CAN IMU 接收 | 旧 schema 3，72 路，20 ms 目标周期 | JustFloat |
| `2`，用途 `0`，未开启 CAN IMU 接收 | 旧 schema 2，64 路，20 ms 目标周期 | JustFloat |
| `2`，用途 `1` | schema 4，96 路，20 ms 最新快照 | JustFloat |
| `2`，用途 `2` | schema 5，96 路；远端融合为调用事件 FIFO，其他配置为 20 ms 最新快照 | JustFloat |

在 [config/90_board/board_config.h](../config/90_board/board_config.h) 中修改 `VOFA_TELEMETRY_MODE` 后，正常编译烧录即可切换协议。构建命令也可显式覆盖该宏。力控模式、裁判使用 UART7 或 UART7 接有辅助设备时，默认关闭 VOFA+ 输出。USB 遥测可同时开启，也可用 `USB_TELEMETRY_ENABLE=0` 单独运行无线遥测。[A 板串口接线](atype-integration.md#接线)

当前使用 **双 A 板，默认 CAN1、ID `0x180`**：下方板专门采样、温控并以 50 Hz 发送 IMU，主板接收并进行只读卡尔曼观测。DM 模块接收与换算路径已移除。接线、两板构建与 116 mm 安装补偿见 [双 A 板说明](dual-a-imu-integration.md)。

日常构建使用 [`config/00_flash/board_flash_config.h`](../config/00_flash/board_flash_config.h)，主板为 `BOARD_FLASH_1_`，下方采集板为 `BOARD_FLASH_2_`。分别构建和烧录到对应物理板，采集板不运行整车任务。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-board.ps1 -Action Show
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-board.ps1 -Action Build
# 连接所选物理板；构建成功后再烧录同一输出目录的固件
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-board.ps1 -Action Flash
```

用 `-Board 1` 选择主板，`-Board 2` 选择采集板。下载器用法见 [配置目录说明](../config/README.md#主板怎样构建与烧录)。F5 的 ST-Link / DAPlink / Jlink 通过 `build selected board for debug` 读取 `BOARD_FLASH_TARGET` 对应预设并构建；`DAP-attach` 固定使用主板已有 ELF，不构建或烧录。手动 Make/CMake 不读取板卡预设，构建示例：

```powershell
make -j8 PROFILE=atype-vehicle BUILD_DIR=build/kalman-main ONE_BOARD=1 CHASSIS_CONTROL_MODE=0 CHASSIS_IMU_CAN_RX_ENABLE=1 CHASSIS_VELOCITY_FUSION_ENABLE=1 CHASSIS_REMOTE_IMU_FUSION_ENABLE=1 CHASSIS_VELOCITY_FUSION_CALIBRATED=0 VOFA_TELEMETRY_ENABLE=1 VOFA_TELEMETRY_MODE=2 VOFA_OBSERVATION_PROFILE=2
```

功率采集将最后一个参数改为 `VOFA_OBSERVATION_PROFILE=1`，输出目录改为 `build/power-main`。CMake 接受同名 `-DVOFA_OBSERVATION_PROFILE=1` 或 `2`；手动 Make/CMake 不读取 `BOARD_FLASH_1_` 前缀预设。新档输出 `I0=4/5`，旧 `I0=2/3` 不能套用新布局。

固定安装、芯片偏移和滤波噪声见 [远端 IMU 配置](../config/30_velocity_observation/chassis_remote_imu_config.h)。远端融合采用以底盘中心为原点的 A 板原生轴，芯片偏移 `(0,+0.116,0) m`、安装四元数 `[1,0,0,0]`。轮速、目标速度、融合速度和配对轮速的 VOFA 公共接口保留原有定义；依据四份实测 CSV，融合入口按 A 板 `(+vx,+vy)` 处理公共轮速，出口和配对轮速保持 X/Y 同号，不再对 X 取反。公共字段与实物方向仍需实车核对。`CHASSIS_REMOTE_IMU_CONFIG_VERIFIED=0` 不会阻止算法运行，但不能用于证明精度。

需要纯采集对照时，只把 `BOARD_FLASH_1_CHASSIS_REMOTE_IMU_FUSION_ENABLE` 改为 `0`；手动命令同样仅将 `CHASSIS_REMOTE_IMU_FUSION_ENABLE=0` 并改用独立构建目录。双板 CAN 传输与主板遥测继续运行。

若另行验证主板原有的本地云台 IMU 融合路径，必须关闭远端接收及远端融合，提供目标车实测的 `chassis_velocity_fusion_calibration.h`，再设置 `CHASSIS_VELOCITY_FUSION_CALIBRATED=1`；不使用 `tests/.../stubs` 的合成参数代替实车标定。

模式 `1` 与模式 `2 + profile 0` 使用相同的旧 schema 2/3 通道顺序、缩放单位和有效位。模式 `0` 的 19 路 JustFloat 格式保持兼容。仅检查本地 IMU 时使用文末的[本地 UART 诊断](#本地-imu-uart-诊断)，显式选择用途 `0`。

当前整车默认直供。已接入匹配的 F334 超电且整车使用超电供电时，构建时设置 `CHASSIS_POWER_SOURCE_MODE=1`。切换观测用途不会改变供电方式。[超电协议](supercap-can-protocol.md)

## 新档通道与分析约定

新 schema 4/5 的唯一通道定义在 [`config/32_capture/vofa_schema.json`](../config/32_capture/vofa_schema.json)，按数组顺序对应 `I0`–`I95`；解析器使用同一文件。用户只需保存全部通道。四轮数组统一为 **LF/RF/LB/RB**，物理量直接采用 W、J、转子 rpm、m/s、m/s²、rad/s；DJI 命令与反馈为原始计数，不是安培。旧 schema 的缩放和有效位不适用于新档。

可直接查阅自动生成的[两档通道表和有效位](vofa-observation-channels.md)。工程维护者修改 JSON 后运行 `python scripts/generate-vofa-schema.py`；`--check` 同时检查固件索引与文档是否同步。

32 位时钟和计数以高/低 16 位发送，按 `高位×65536+低位` 还原并按 uint32 回绕处理。年龄未知为 `-1`，无效测量的占位零不能当成真实零值。滤波时钟为 uint32 微秒时钟，约 71.6 分钟回绕；与板端毫秒时钟分别处理。帧尾冲突处理可能改变浮点数最低尾数位，计数还原前先四舍五入。

功率档分别标识控制周期实际使用的预算/修正与发送时最新策略，保留周期、版本和年龄；最新策略不能假定与最后电机周期同时生效。最终整数 CAN 命令与提交状态分别记录，提交成功不代表电机已经执行。功率计的事件号、功率和年龄来自该控制周期采用的测量。超电目标与回显相等只说明数值一致，不能单独作为强命令确认；协议不提供电容内部电压、电流和温度。

卡尔曼档 `imu_source=1` 表示第二块 A 板，`0` 为本地来源；旧 DM 来源 `2` 不再由当前双板固件输出。

卡尔曼档的 `wheel_n_x_mps/y_mps` 与 `accel_n_x_mps2/y_mps2` 记录实际调用生产滤波器前的同一导航系输入。它们来自三点补偿的中间样本，和原始 IMU 快照分开。被滤波器拒绝的调用也保留输入与返回结果。重放依据该次尝试保存的 `resets_before` 与初始化状态；后验速度减轮速仅是后验差值，不是校正前 innovation。

远端融合且 `mode=2/profile=2` 时，观察器每次真正调用滤波器后，将输入、输出、配置、原始 IMU、目标速度和采集时刻一起复制到 16 槽 FIFO。生产者只做有界复制，编码由低优先级遥测任务完成。任务每 1 ms 检查串口，原 USB/信息收集仍每 20 ms 执行。388 字节在 230400/8N1 下占线约 16.84 ms；队列可缓冲约 0.32 s 的 50 Hz 调用，但持续串口故障或更长停顿仍会溢出。

新模式 `I5` 的 bit 6（`capture_fifo`）为 1，bit 7（`capture_overflow`）表示本次主板启动后曾发生队列溢出。`I1/I2` 是采集时刻，所有年龄/有效位按该时刻计算，不含排队延迟；`I3/I4` 是捕获记录序号，溢出时也递增，因而后续记录可显示缺口。队列满时丢弃新记录并累计次数，不覆盖旧记录。串口忙或提交失败保留队头；仅提交成功后出队，正在发送的缓冲区不被改写。`VofaKalmanCaptureGetStats()` 可读取入队/已发送/丢弃/发送失败/待发送/队列峰值计数。

状态改变和 100 ms 没有新调用时也保存诊断记录，所以启动/预热/故障期间仍可见数据，可能重复同一滤波调用序号；分析器会去重。不会在遥测任务启动时清空先到的首个滤波调用。未开启远端融合的 schema 5 及旧版记录仍是最新快照，不能保证包含每次滤波调用。

每帧带配置来源、版本和本档必要的实际参数。分析先核对参数身份；功率侧可能受 Flash/在线覆盖影响，不能只按源码默认值解释。参数无法追溯、输入缺口过多或连续段不足时，只报告限制并补采，不给出声称已验证的最优参数。

## 双 A 板 CAN 接线与传输

两板按 `CHASSIS_IMU_CAN_PORT` 选择 CAN1 或 CAN2（默认 CAN1），所选接口的 CAN_H 对 CAN_H、CAN_L 对 CAN_L，并连接参考地，速率 1 Mbps；按总线两端配置终端电阻。采集板使用 `IMU_CAPTURE_ONLY=1 IMU_CAPTURE_CAN_TX_ENABLE=1`，主板启用接收，标准 ID 为 `0x180`。

采集任务名义每 20 ms 尝试发送一组，共 9 个 8 字节分片，携带源序号、源时间和源年龄。主板校验顺序、同组 tag、CRC16 与 10 ms 组装期限，错序/缺片/过期组不刷新样本。源 INS 已输出去重力加速度，主板不再做 DM 重力换算；安装补偿只作用于融合输入。[接线与首次核对](dual-a-imu-integration.md)

## 连接调试器

1. 将塔克调试器的无线主机插到电脑 USB 口，接收端设为无线从机。普通款主机的 STA 灯为蓝色，从机为绿色。若尚未配对，按手册第 2.2 节完成配对并给两端重新上电。
2. 只连接**主板 UART7**：在 A 板位号 `16` 的串口组找到最右侧、丝印 `7` 的接口。接线前按 A 板和调试器的丝印核对引脚。[UART7 接口位置](referee-uart7-fix.md)

   | A 板 UART7 | 无线从机 |
   | --- | --- |
   | `TX`（PE8） | `RX` |
   | `GND` | `GND` |
   | `5V`（从 A 板取电时） | `5V` |

   单向遥测只需要上表中的连线。调试器引脚和供电方式见[《塔克无线高速 DAP 调试下载器手册 V3.0.1》](<../reference-data/塔克 l 无线高速DAP调试下载器手册V3.0.1.pdf>)第 1.4、2.4.1 节，手册推荐从机使用 5 V 供电。

3. 上电后在 Windows 设备管理器的「端口（COM 和 LPT）」里确认主机新增的虚拟 COM 号。对应示意见手册第 2.5 节。

## 在 VOFA+ 中连接

1. 连接方式选 **SerialPort**，选择主板调试器的虚拟 COM 号，模式 `2` 设为 **230400、8 数据位、无校验、1 停止位、无流控**；模式 `0/1` 保持 **115200**。双板数据统一使用主板这一个接收通道。
2. 当前主板模式 `2` 选择 **JustFloat**，再打开串口。右侧数据栏以 `I0`、`I1` 等显示通道，点击通道名可重命名。字节接收区勾选 `Hex` 查看二进制数据；波形和通道值仍正常显示数字。模式 `0` 同样选 JustFloat；仅模式 `1` 选 **FireWater**，并关闭 `Hex` 查看逗号分隔文本。[JustFloat 协议](https://www.vofa.plus/docs/learning/dataengines/justfloat/)、[FireWater 协议](https://www.vofa.plus/docs/learning/dataengines/firewater/)
3. 主板与 IMU 上电后先保持静止。新功率档确认 `I0=4`，新卡尔曼档确认 `I0=5`，通道数均为 96；以各档有效位和年龄判断传感器可用性。卡尔曼记录可含预热、拒绝和轮速回退，不必删除这些行。
4. 从控件栏拖入「波形图」，在 Y 轴菜单勾选要看的通道。功率档可先看计量功率、目标/有效上限及超电输入/输出；卡尔曼档可看轮速、融合速度及真实配对加速度。字段位置以 [schema 定义](../config/32_capture/vofa_schema.json) 为准，无需重命名后才能导出。实际周期和缺帧由板端时间与发送序号判断。[VOFA+ 波形图操作](https://www.vofa.plus/docs/learning/widgets/wave/)
5. 采完后用 VOFA+ 的 **文件 → 保存数据** 将完整 **`I0`–`I95`** 保存为原始 `.csv`。保留默认或已重命名的表头以及 VOFA 时间列。切换用途或开始下一试次前，保存上一批并清空缓冲区；不同 schema 分别保存。旧模式仍按各自表格保存 19/64/72 通道。

模式 `2` 的串口数据没有逗号或文本换行，VOFA+ 按二进制帧尾解析为完整的一组通道，再按组导出 CSV。模式 `1` 的文本接收区可能按窗口宽度折行，但每组在串口上仍只有一个行末换行。

### 230400 波特率的使用与影响

提高波特率只作用于启用模式 `2` 时的 UART7；模式 `0/1`、VOFA 关闭时的 UART7 初始化，以及其他串口保持原设置。切回旧模式时，VOFA 的波特率也要改回 115200。固件、VOFA 和无线从机的串口速率须匹配；只改电脑端不能证明整条链路已正确配置。

《塔克无线高速 DAP 调试下载器手册 V3.0.1》未明确给出串口支持波特率上限，也未保证电脑端设置自动同步到从机。`CONF.TXT` 的 `rate` 表示空中速率，不是 UART 波特率；手册的无线下载速度也不是串口透传吞吐保证。使用无线链路前确认设备支持并匹配 230400，以板端时间与发送序号验证持续接收；本次配置没有上板实测保证。

新档 96 路加帧尾共 `96×4+4=388` 字节，50 Hz 时约 **19.4 kB/s**；230400 / 8N1 下单帧线占用约 **16.84 ms**，小于 20 ms。固件静态检查通道与线速预算，仍采用异步发送和忙时整帧跳过。当前逐字节 `HAL_UART_Transmit_IT` 约需 19400 次发送空中断/秒，另有帧完成中断；实际 CPU 占用、任务延迟、无线吞吐与持续丢帧须上板测量，静态预算通过不等于完成这些验证。

采集前核对模式 `2`、230400 / 8N1，再连续记录并检查相邻板端时间是否以约 20 ms 为主、发送序号有无缺口，以及控制任务是否新增超时。发生丢帧时先核对两端波特率、无线链路和接线，不跨缺口插值后当成真实连续采样。

## 原有 19 路 JustFloat 通道表（模式 0）

| 通道 | 数据 | 单位 |
| --- | --- | --- |
| `ch0`–`ch3` | LF、RF、LB、RB 电机转子实测转速 | rpm |
| `ch4`–`ch7` | LF、RF、LB、RB 电机转子目标转速 | rpm |
| `ch8` | 功率计实测功率 | W |
| `ch9` | 限制后模型估算功率 | W |
| `ch10` | 有效功率上限 | W |
| `ch11` | 超级电容输出侧底盘功率 | W |
| `ch12` | 超级电容输入功率 | W |
| `ch13` | 超级电容剩余百分比 | % |
| `ch14`–`ch16` | IMU 的 yaw、pitch、roll | ° |
| `ch17` | 电机在线位掩码，bit 0–3 对应 LF、RF、LB、RB | — |
| `ch18` | 数据有效位掩码，见下文 | — |

LF、RF、LB、RB 依次为左前、右前、左后、右后。将转子 rpm 除以 `REDUCTION_RATIO_WHEEL`（默认 19.0）即可换算为轮端 rpm。电机在线位清零时，该电机的实测和目标转速均发送 0。

`ch18` 的 bit 0 对应功控模型（`ch9`、`ch10`），bit 1 对应功率计（`ch8`），bit 2 对应电容输出与剩余百分比（`ch11`、`ch13`），bit 3 对应电容输入（`ch12`），bit 4 对应 IMU（`ch14`–`ch16`）。数据不可用时发送 0，可结合有效位区分真实零值。

每帧由 19 个小端 32 位浮点数和 `00 00 80 7F` 帧尾组成，共 80 字节。数据字节若恰好拼成帧尾，固件会调整冲突浮点数的最低尾数位，避免接收端提前切帧。发送周期跟随 `USB_TELEMETRY_PERIOD_MS`，默认 20 ms（50 Hz）。UART7 忙时跳过当期整帧。[JustFloat 解码器](https://github.com/je00/Vodka/blob/master/dataengines/justfloat/justfloat.cpp#L39-L50)

## 旧完整观测通道表（模式 1，或模式 2 + profile 0）

本节的 schema 2/3、列号、缩放和有效位仅解释旧格式；新 schema 4/5 使用前述 JSON 定义。下面各小节直到“CSV 采集与交付”均为旧格式说明。

外部 CAN IMU 主板使用 **schema 3，每帧固定 72 路**；未开启远端接收时为 schema 2，每帧固定 64 路。模式 `1` 与 `2 + profile 0` 使用下表同一组通道、单位和有效位，整帧组好后一次提交给 UART7，串口为 **8N1**，模式 `2` 使用 **230400**，模式 `1` 保持 **115200**。

- 模式 `2`：64/72 个小端 float32 加 `00 00 80 7F` 帧尾，分别为 260/292 字节；目标发送周期 20 ms，标称 50 Hz。230400 / 8N1 下，72 路一帧线速传输约需 12.67 ms，20 ms 周期占用约 63.4% 串口带宽；64 路分别为 11.28 ms 和 56.4%。默认遥测任务周期仍为 20 ms。
- 模式 `1`：64/72 个十进制整数以逗号分隔，仅最后一列后加换行（LF）；发送间隔至少 80 ms，标称 12.5 Hz，保留原有 FireWater 行为。

UART7 忙时跳过整帧，后续发送尝试序号会出现缺口。CSV 由 VOFA+ 采集后导出；模式 `2` 按 20 ms 目标周期尝试发送最新快照，未改变 IMU、CAN 接收或融合器的内部更新率。即使输入名义频率也是 50 Hz，异步相位、调度抖动和链路延迟仍可能造成重复或漏采，不能保证每个输入样本都出现在 CSV 中。

模式 `2` 按固定 20 ms 时槽推进，轻微迟到仍保持周期相位；例如板端发送时刻可能为 0、21、40、61 ms，相邻间隔可为 19/21 ms，20 ms 不是最短间隔保证。长暂停后只发送最新快照，不补发旧帧；任务实际阻塞或 UART 忙仍可能漏组。

模式 `2` 先按表中单位生成整数测量值，再转成 float32，未改成 SI 浮点单位。float32 仅保证 `[-16777216,16777216]` 内的所有整数可精确表示，极端大整数会舍入。为避免数据字节误触帧尾，固件可能调整冲突浮点数的最低尾数位。CSV 后处理对序号分段、状态和掩码等整数语义字段先四舍五入再组合或做位运算；分成高低 16 位的时间与计数可据此还原，不能将所有 int32 测量值视为逐位无损。

schema 3 保留前 64 列的布局：`I0` 改为 `3`，`I33`–`I45` 改取远端底盘 IMU，并追加 `I64`–`I71` 的来源与接收诊断。`I63` 仍表示输出观测帧的主板角色，不能据此把 schema 3 的 IMU 判断成本地云台 IMU。

### 时间、年龄与来源

协议携带源板 INS 样本序号 `I34/I35`、源板毫秒时间 `I67/I68` 和发送时源年龄 `I66`。两板独立计时，不能用主板时间直接减源板时间。时间和计数按 `高位×65536+低位` 还原；模式 `2` 先四舍五入并转整数。时钟/序号按 uint32 回绕，拒绝组数饱和，两板重启都要分段分析。

`I33=源年龄+(主板当前时间−首片接收时间)`，是已知年龄下界，不包含传感器内部延迟与首片仲裁前等待。`I65` 为完整组接收年龄，`I69` 为首末片跨度；有效输入还要求 `I66≤20 ms`、`I33≤60 ms`。重复快照不刷新序号/时间，最近一组相同 tag+CRC 的完整重传也不刷新接收样本。

融合用 `首片接收时间−源年龄` 估计主板轮速配对时刻，中心差分和滤波 dt 使用源板采样间隔。输出对应三点补偿的中间样本，旧 `I27/I28` 与 `I29/I30` 才是同一时刻的估计/配对轮速，不能和最新原始输入逐行直接比较。导航系加速度不同于底盘前/右加速度，bit 17 不表示完成硬件同步。

## CSV 采集与交付

每次选一个用途，每个试次保存一份完整原始 CSV。动作前后各保留约 5 s 静止记录，起停和换向过程也保留。初次交付简述实际动作、地面/载荷、直供或超电供电，以及 IMU 安装轴向与芯片偏移；同时保留固件提交号和构建选项。这些是试验背景，不是要求配置 CSV 字段。

### 功率/超电采集动作（profile 1）

| 动作 | 建议时长/重复 | 观察内容 |
| --- | --- | --- |
| 静止，记录当前电机使能状态 | 20–30 s | 功率基线、反馈有效率与参数来源 |
| 低速前后/左右直行，各保持数个稳定速度段 | 每方向 20–30 s，重复 3 次 | 四轮转速与最终命令、稳态功率模型 |
| 从静止平滑加速、保持、松杆停止 | 3–5 次完整动作 | 启动额度、限制/恢复、快保护与慢环响应 |
| 已接入匹配超电时重复同样动作，动作间保留恢复段 | 3 次独立试次 | 输入目标/回显、输入输出功率、剩余比例、缓冲与恢复 |

直供时保留超电无效标记，不把占位零用于拟合；不为产生数据而切换真实供电接线。20 ms 快照可以比较响应阶段，不能声称还原每次快速控制或 CAN 提交历史。

### 卡尔曼采集动作（profile 2）

| 动作 | 建议时长/重复 | 观察内容 |
| --- | --- | --- |
| 底盘与云台静止 | 30–60 s | 静止噪声、偏置、源数据年龄和连续输入段 |
| 云台尽量固定，低速前进/后退并起停 | 30–60 s，重复 3–5 次 | 前向响应、拒绝与重置 |
| 云台尽量固定，低速左移/右移并起停 | 30–60 s，重复 3–5 次 | 横向响应、安装坐标与轮速符号 |
| 零输出手推旋转，或采用已经验证的受限动力配置 | 每方向 20–30 s | 固定安装偏移与旋转期间的中心补偿；默认自旋档不是低速档 |

先核对下方 A 板原生轴向，并完成倾斜静止去重力检查。偏移使用 A 板 +Y 116 mm（已量到芯片），安装四元数为 `[1,0,0,0]`；正反 X/Y 平移应同时检查融合前后的公共速度符号，不能只看单向或静止工况。原生四元数、角速度保持传感器定义，导航系加速度不等于机体系加速度。没有独立速度/位移参考时，CSV 仅支持噪声与响应调试，不能证明真实车速精度或打滑误差。[实测与验收步骤](kalman-chassis-test-and-acceptance.md)

### 从原始 CSV 到参数复采

1. 原文件交给助手。工程解析按 schema、通道数和数据值识别新档及受支持旧档，保留 VOFA 时间列和原表头；缺列、混合 schema 或无法唯一识别时停止并解释，不猜列号。
2. 先检查板端时钟、发送/滤波尝试序号、重启、重复、缺帧、有效率、年龄与实际配置，给出质量报告和可用区间。
3. 功率静态模型复用 `scripts/power_model_*` 的稳态筛选、计量事件去重、拟合与生产 C 对照；慢环/启动/超电参数按完整响应阶段提出候选。卡尔曼按尝试序号去重，只对连续真实输入段使用生产 C 滤波器重放，遇缺口或重置重新预热，不插值补造板上输入。
4. 报告参数旧值/候选值、证据、适用工况与待验证项。数据不足或配置无法追溯时要求补采；不同时任意缩放 Q/R 后把相同输出称作改善。
5. 数据充分后修改对应配置，完成相关测试和固件构建，创建本地提交。用户烧录后以相同动作做新的独立试次，再比较修改前后；不把随机拆分的相邻数据行当作独立验证试验。

旧版/非远端融合的 50 Hz 最新快照仍不保证包含每次滤波调用。新 FIFO 记录应检查 `capture_mode=event_fifo`、无 `capture_overflow_observed`、无记录序号和滤波调用缺口。FIFO 只能保存主板实际发生的调用，不能补回上游 CAN 未收到的 IMU。连续段若从已经初始化的滤波状态中途开始，重放的预热段不能当作精确板上状态复现；应从主板初始化前开始记录，并保留完整动作段。

### 工程分析命令

以下步骤由助手或工程维护者完成，采集者仍只需提供原始 CSV 和动作背景。基础解析和卡尔曼重放使用 Python 标准库及主机 GCC；功率拟合安装工程已经固定版本的依赖：

```powershell
python -m venv build/vofa-python
& build/vofa-python/Scripts/python.exe -m pip install -r scripts/power-model-requirements.txt
& build/vofa-python/Scripts/python.exe scripts/analyze-vofa.py '原始记录.csv' --output-dir build/vofa-analysis/run01
```

输出目录必须是新目录，生成 `report.json` 和可读的 `report.md`；错误数据同样生成拒绝原因。旧 schema 2/3 可以检查质量与旧单位，但缺少真正配对输入，不做新档的精确滤波重放。当前原始导出兼容性由合成 CSV 与固件序列化测试覆盖，真实 VOFA 导出样本仍需首次实车采集核验。

卡尔曼静止记录可加 `--stationary`，这个选项表示已经根据实际动作确认静止，不从低轮速自动推断。候选参数通过 `--fusion-candidate candidate.json` 传入，例如以下文件仅示例格式，不是实车参数建议：

```json
{"fusion_wheel_variance": 0.02}
```

候选与原参数使用相同真实输入段，分别报告预热、拒绝、回退和噪声等指标。配置中的轮速方差、加速度方差、jerk 密度与残差门限来自那次实际调用；`config_fingerprint` 是完整安装/滤波/时限配置的稳定身份。发送时最新 IMU 的已知年龄为源年龄加上首帧接收至当前的间隔，`imu_receive_age_ms` 则从完整组最后一帧接收时间计算，均不能消除传感器内部延迟和首片仲裁等待的不确定度。

功率配置必须匹配 CSV 中的指纹、配置版本和来源。`scripts/vofa_config.py` 使用生产 C 构造与哈希完整参数，支持编译默认、文件覆盖以及已有 USB 调参协议的原始 `@T1` power 回复：

```powershell
python scripts/vofa_config.py --output build/power-config.json
# 若CSV来源为Flash，助手取得现有USB调参协议的GET power回复后：
python scripts/vofa_config.py --source flash --config-version 7 --tuning-reply build/power-get-reply.txt --output build/power-flash-config.json
python scripts/analyze-vofa.py '功率记录.csv' --configuration build/power-config.json --output-dir build/vofa-analysis/power01
```

配置版本 `7` 只是命令格式示例，必须换成 CSV 的真实版本；构建覆盖通过重复的 `--define NAME=VALUE` 传给配置导出器。没有匹配配置时仍可输出质量和响应诊断，但不拿源码默认模型冒充实际模型。UART7 保持单向遥测，不增加控制命令。

静态模型拟合用 `--power-trials trials.json` 指定由助手整理的独立完整试次及仪表误差，另加 `--configuration`。试次文件的相对路径以该 JSON 所在目录为基准，每个试次指定 `id`、`path`、`session`、`split`（`train` / `calibration` / `test`）与 `synthetic`（真实采集为 `false`）；顶层提供 `instrument_error_w` 与 `trials`。工具输出经过生产 C 对照的候选 `model.json`，不会自动安装或宣称完成硬件验证。对应实车工况、慢环/启动/超电阶段与修改前后的独立复采，仍由助手结合质量报告解释后决定修改。

## 本地 IMU UART 诊断

`IMU_CAPTURE_ONLY=1` 仅运行本板 IMU 采样、温控和所选传输，不启动整车电机/遥控任务。下述本地 UART 诊断显式关闭 `IMU_CAPTURE_CAN_TX_ENABLE`，只检查本板；双板采集预设则开启该发送开关，关闭 UART/USB 遥测，由主板统一记录。

```powershell
make -j8 PROFILE=atype-vehicle BUILD_DIR=build/imu-local-diagnostic IMU_CAPTURE_ONLY=1 IMU_CAPTURE_CAN_TX_ENABLE=0 CHASSIS_IMU_CAN_RX_ENABLE=0 CHASSIS_REMOTE_IMU_FUSION_ENABLE=0 CHASSIS_VELOCITY_FUSION_ENABLE=0 VOFA_TELEMETRY_ENABLE=1 VOFA_TELEMETRY_MODE=2 VOFA_OBSERVATION_PROFILE=0 USB_TELEMETRY_ENABLE=0
```

输出 schema 2/64 列，`I63=1`、`I6=-2`、bit 14=1；只有本地 IMU 相关测量有效，控制/轮速列不可用。完整保存 `I0`～`I63`，不能把这一诊断固件当作正常整车固件。恢复整车时重新构建并烧录主板预设。
